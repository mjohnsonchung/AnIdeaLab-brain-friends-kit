# Brain update 3 from AnIdeaLab: every skill in a list by topic, a check against the kit, and a daily update check

Sent 26 Oct 2026. Every skill, the brain's own included, gets a line in a list by topic; the scripts tell copied skills from the brain's own by one record instead of by headings; a new step checks the whole brain against the kit as it should be; and the brain checks for updates once a day.

## Summary for the owner
- Every skill now has its line in a list by topic, your brain's own first, so an agent with a job opens one list and sees everything for it. The skills list keeps only the few most jobs need.
- One list, `skills/lists/sources.md`, now says which skills were copied from elsewhere, and the brain's checks read it.
- Your agent can check your whole brain against the kit as it should be after this update, and the report it sends AnIdeaLab says how close it is. It still leaves out your notes, projects and people.
- Your brain checks for updates from AnIdeaLab once a day, when you start a session, and says nothing unless there is one. Then your agent tells you, and you decide, as now.

Nothing runs on your PC.

## What changed, and why
- **Every skill has a line in a list by topic** (`skills/README.md`, `skills/lists/`). Matt, 26 Oct 2026: "I actually thought that the skills list was set up with just every skill going under subjects... I thought the brain's own skills get sorted into that index list as well." Until now the brain's own skills had their lines on the skills list and the copied ones in topic lists, so an agent with a job looked in two places. Now every skill has one line, in the list for the job it serves most, and in each list the brain's own come first under a "The brain's own" heading, with the copied ones below. Why a group at the top: the brain's own were written for this brain, so an agent should read them before a copied one on the same job, and they're changed freely while a copied one stays as it came, which an agent must know before it edits one. The kit's six moved: getting-started, guide-mode, brain-spec, brain-audit and my-pc into a new list, "The brain and your PC" (`lists/the-brain.md`), and find-skills to the top of "AI, Claude and skills". The skills list keeps the four most jobs need (brain-spec, guide-mode, my-pc, find-skills) and links every list under "The lists by topic". Matt's own brain made the same change the same day.
- **Copied skills are told apart by a record, not by headings** (`check_links.py`, `library.py`, `skill_updates.py`). The scripts used to work out which skills were the brain's own from the headings on the skills list. That was fragile: in one brain a list linked under both headings made the link check report 32 broken links inside copied skills, and update 2 could only fix that one case. Now `skills/lists/sources.md`, which already named every copied skill under its source, is the record: a skill it names is copied, and any other skill is the brain's own. `skill_updates.py` reads source lines only there, and `library.py check` now reports a skill with no line in a topic list, and a source's "From" line with a commit anywhere but `sources.md`. Why: one place to say a skill is copied can't disagree with itself, and it doesn't break when someone renames or moves a heading.
- **A check against the kit: `brain_update.py compare`** (from this update on, and `finish` runs it). Matt, 26 Oct 2026: "I do think that there should be an actual exemplar of how it's all set up. The update the agent can check against." The exemplar is the kit repo's `brain/` as it is at each update; for this one, [https://github.com/mjohnsonchung/AnIdeaLab-brain-friends-kit/tree/9d71b87f2aec2625981acbf6123b82789c165163/brain](https://github.com/mjohnsonchung/AnIdeaLab-brain-friends-kit/tree/9d71b87f2aec2625981acbf6123b82789c165163/brain), and `compare` prints it too. Why: an update only changes the files it touches, so a brain that drifted somewhere else stays drifted, and nothing showed it. `compare` lists every file that should match the kit exactly (the scripts, workflows, the kit's own skills, the copied skills, the brain graph) and differs or is missing, and checks the shape of the files the owner fills in (the core, the front door, the skills list and lists, the knowledge library): the kit's headings are there, each shelf's index has its markers, and every skill has one line in a topic list, in the right group. `compare --diff <file>` shows a difference, and `compare --take <file>` puts the kit's copy in. It prints counts and the kit's file names; the owner's own notes and files are counted, never named.
- **The daily update check** (`reminders.py`, `brain_update.py notice`). Matt, 26 Oct 2026: "let's make the friends kit check daily for updates, but silently unless there is one, in which it prints a message to the owner when he sends a message". Until now only the weekly tidy-up looked, and only once the owner said yes to it. Now the check Claude Code runs as a session starts (`reminders.py`, through `.claude/settings.json`) also runs `brain_update.py notice`. That asks the kit repo at most once a day, remembering the answer on the computer (`~/.cache/brain-updates/`), not in the brain, and prints only when an update is waiting, so the agent tells the owner in its first reply. If github.com doesn't answer in a few seconds it says nothing, and asks at the next session. Any other agent gets the same by running `reminders.py`, as the core says. The routines note has its row.
- **Smaller changes:** the core's line on the skills list, and on telling the owner when an update is waiting; the brain spec's "A skill" and "Brain updates", find-skills' step 6 and the tidy-up's step 8 say all of the above; Obsidian's skills are in `skills/sources/upstream.json` now, so `skill_updates.py check` checks them too.

## What to do beyond the files
1. **Read both sides of each clash the script printed.** The script that applied this update is the copy update 2 left, which prints them. Put back what's the owner's own, and let the brain's own earlier fixes to kit parts go, by the brain spec's "Brain updates" and for its reasons. If the owner changed the skills list or the kit's lists, those will clash: keep the update's shape, the setup above, and fit the owner's lines into it in the next step.
2. **Fit the owner's own skills and lists into the topic lists.** For every skill folder the kit didn't bring:
   - **One of the brain's own** (the owner, or an agent for them, wrote it): give it a line under "## The brain's own" at the top of the topic list for its job. Start that heading if the list has none, and put "## Copied" above the copied lines. Leave it off the skills list, unless most of the owner's jobs need it.
   - **A copied one** (it came from a GitHub repo, often with a "From [owner/repo](...), commit `...`" line above it): give it a line in the topic list for its job, and a line under its source in `skills/lists/sources.md`. Move the source's "From" line, with its commit, date and licence, out of the owner's list and into `sources.md` under a new heading, `## owner/repo`, with the source's skills one line each below it; leave what the list said about using the set (what it needs, what it's for, a GPL or other licence note) in the topic list. Then run `python3 skills/brain-spec/skill_updates.py map`. If you can't tell where a skill came from, look at the commit that added it (`git log --diff-filter=A -- skills/<name>/SKILL.md`), and if that doesn't say, treat it as copied and say so in the report.
   - **A list of the owner's own** (a video list, say): keep it as a topic list, linked from the skills list under "The lists by topic", unless one of the kit's lists is plainly the same topic; then move its lines there. Either way, each skill has one line.
   - Why: the scripts now take every skill `sources.md` doesn't name for the brain's own, so a copied skill missing from it would be held to the brain's own rules (its links checked, a 500-line limit, lessons folded into its text), which is what gave one brain 32 false broken links. And agents find a skill through the topic lists, so a skill with no line there is as good as missing.
3. **Run `python3 skills/brain-spec/brain_update.py compare`.** The copy that applied this update didn't have it; the copy this update brought does. It compares the whole brain with the kit's brain at update 3, the exemplar: [https://github.com/mjohnsonchung/AnIdeaLab-brain-friends-kit/tree/9d71b87f2aec2625981acbf6123b82789c165163/brain](https://github.com/mjohnsonchung/AnIdeaLab-brain-friends-kit/tree/9d71b87f2aec2625981acbf6123b82789c165163/brain).
   - A file that should match the kit and differs: if it's the brain's own earlier fix or workaround for a kit part, take the kit's copy (`compare --take <file>`). If it's one of the kit's own skills with a lesson folded in by the weekly tidy-up, take the kit's copy too, and put the lesson back in that skill's `LESSONS.md` as a dated line, so it isn't lost and Matt can bring it into the kit. If it holds something of the owner's own (their PC's folder in a command, say), keep their line and say so in the report.
   - A file that should match the kit and is missing: put it back with `compare --take <file>`, unless the owner deleted it on purpose (a copied skill they didn't want, say); then leave it out, and say so in the report.
   - A shape problem: fix it as the setup above says. The core's "Guide mode is on" heading is missing if the owner turned guide mode off; that's theirs, and stays.
   - Why: the kit is tried on a brain like the exemplar, so the closer this brain is to it, the more surely each update works here, and the fewer clashes cost the owner's usage next time.
