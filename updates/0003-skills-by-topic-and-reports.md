## What changed, and why
- **Every skill has a line in a list by topic** (`skills/README.md`, `skills/lists/`). Matt, 26 Oct 2026: "I actually thought that the skills list was set up with just every skill going under subjects... I thought the brain's own skills get sorted into that index list as well." Until now the brain's own skills had their lines on the skills list and the copied ones in topic lists, so an agent with a job looked in two places. Now every skill has one line, in the list for the job it serves most, and in each list the brain's own come first under a "The brain's own" heading, with the copied ones below. Why a group at the top: the brain's own were written for this brain, so an agent should read them before a copied one on the same job, and they're changed freely while a copied one stays as it came, which an agent must know before it edits one. The kit's six moved: getting-started, guide-mode, brain-spec, brain-audit and my-pc into a new list, "The brain and your PC" (`lists/the-brain.md`), and find-skills to the top of "AI, Claude and skills". The skills list keeps the four most jobs need (brain-spec, guide-mode, my-pc, find-skills) and links every list under "The lists by topic". Matt's own brain made the same change the same day.
- **Copied skills are told apart by a record, not by headings** (`check_links.py`, `library.py`, `skill_updates.py`). The scripts used to work out which skills were the brain's own from the headings on the skills list. That was fragile: in one brain a list linked under both headings made the link check report 32 broken links inside copied skills, and update 2 could only fix that one case. Now `skills/lists/sources.md`, which already named every copied skill under its source, is the record: a skill it names is copied, and any other skill is the brain's own. `skill_updates.py` reads source lines only there, and `library.py check` now reports a skill with no line in a topic list, and a source's "From" line with a commit anywhere but `sources.md`. Why: one place to say a skill is copied can't disagree with itself, and it doesn't break when someone renames or moves a heading.
- **A check against the kit: `brain_update.py compare`** (from this update on, and `finish` runs it). Matt, 26 Oct 2026: "I do think that there should be an actual exemplar of how it's all set up. The update the agent can check against." The exemplar is the kit repo's `brain/` as it is at each update; for this one, linked at the end of this message, and `compare` prints it too. Why: an update only changes the files it touches, so a brain that drifted somewhere else stays drifted, and nothing showed it. `compare` lists every file that should match the kit exactly (the scripts, workflows, the kit's own skills, the copied skills, the brain graph) and differs or is missing, and checks the shape of the files the owner fills in (the core, the front door, the skills list and lists, the knowledge library): the kit's headings are there, each shelf's index has its markers, and every skill has one line in a topic list, in the right group. `compare --diff <file>` shows a difference, and `compare --take <file>` puts the kit's copy in. It prints counts and the kit's file names; the owner's own notes and files are counted, never named.
- **The daily update check** (`reminders.py`, `brain_update.py notice`). Matt, 26 Oct 2026: "let's make the friends kit check daily for updates, but silently unless there is one, in which it prints a message to the owner when he sends a message". Until now only the weekly tidy-up looked, and only once the owner said yes to it. Now the check Claude Code runs as a session starts (`reminders.py`, through `.claude/settings.json`) also runs `brain_update.py notice`. That asks the kit repo at most once a day, remembering the answer on the computer (`~/.cache/brain-updates/`), not in the brain, and prints only when an update is waiting, so the agent tells the owner in its first reply. If github.com doesn't answer in a few seconds it says nothing, and asks at the next session. Any other agent gets the same by running `reminders.py`, as the core says. The routines note has its row.
- **Smaller changes:** the core's line on the skills list, and on telling the owner when an update is waiting; the brain spec's "A skill" and "Brain updates", find-skills' step 6 and the tidy-up's step 8 say all of the above; Obsidian's skills are in `skills/sources/upstream.json` now, so `skill_updates.py check` checks them too.
- **Reports send on a push** (`skills/brain-spec/brain_update.py`, `send`). On a push, `send` worked out which reports the push added from the file lists in GitHub's push event. GitHub leaves those lists out of the event it gives Actions ([its changelog, 16 Oct 2019](https://github.blog/changelog/2019-10-16-changes-in-github-actions-push-event-payload/)), so it always found none, printed "No reports to send." and passed. A brain's update 2 report found it: its push and update 1's had both passed and sent nothing, and its agent sent them by running the workflow by hand. Now `send` fetches the commit from before the push and asks git which reports changed between it and the commit pushed. If git can't say (a new branch, or GitHub doesn't answer), it sends every report, and the inbox replaces any it has already. Matt tried it with a real push on GitHub: the event had no file lists, the old way found nothing, and the new way found both reports the push added. Run by hand, the workflow still sends every report. The brain spec's "Brain updates" now says to check, after pushing, that the run's log says "Sent" with the report's name, and to run the workflow by hand if it doesn't. Why: the run passed while sending nothing, and nobody saw it for two updates.
- **Matt's testing account** (`knowledge/systems/keys-and-accounts.md`, `skills/my-pc/check-setup.ps1`). Matt decided on 27 Oct 2026 that while the kit is in testing, the installer invites his testing account, `diagnoticsanidealab`, to each new brain as a collaborator, so he can see it and copy it to find what's wrong. Brains made before then don't have it, and Matt is sending their owners one command to add it, for them to run if they agree. Why: the accounts note says who can reach the brain, and the setup check warns about anyone else who can write, so both should name the account plainly. GitHub gives a collaborator on a personal account's repo read and write, so the row and the check both say so, and how to take it off.

- **No rules about personal information** (`CLAUDE.md`, `knowledge/decisions/the-brain/<the brain's start date>-starting-rules.md`). Matt, 27 Oct 2026: "You want to free the brain. You want it to be the hub, so it can hold whatever, like mine", since a rule against it "stops them from using the brain the way they want to and is unecesarily restrictive on agents and inefficient too re token use". The kit never wrote a rule against personal information, but its starting rules left out Matt's own default, "no rules about personal information", so agents fell back on their own caution and held back from saving people's details, or spent the owner's usage weighing them. Now the core's defaults have the line Matt's brain has, and the starting rules move it from "left out on purpose" to "kept". The secrets gate stays as it was. Why: a brain is a private repo whose job is to know the owner's life and work, and it can't if agents won't write down who people are.

- **A new skill of the kit's own: `windows-powershell`** (`skills/windows-powershell/SKILL.md`, a line in `skills/lists/the-brain.md`, and the my-pc skill's quirks line pointing to it). Matt, 27 Oct 2026: "make a PowerShell skill... and have those quirks recorded... it keeps tripping you up. I've seen it happen multiple times." Windows PowerShell 5.1, the one on every Windows PC and the runner's default shell, strips double quotes from arguments on their way to programs like `gh` and `git`, fails a whole script on `"$name:"` in a string, turns a program's stderr into errors, and more; agents in Matt's brain kept hitting them. No provider's skill covers them, so the kit has its own, from Microsoft's documentation and those failures, with a check to run before handing a script over. Why: a script that fails on one of these costs the owner a run on their PC and a round of fixing, every time. The kit has 61 skills now.
