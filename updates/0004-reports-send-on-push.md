# Brain update 4 from AnIdeaLab: reports send when you push, and Matt's testing account

Sent 27 Oct 2026. A fix: the report your brain writes after each update never went to AnIdeaLab when it was pushed, and now it does. Your brain's accounts note and setup check also know Matt's testing account, which he's asking friends to add to their brains while the kit is in testing.

## Summary for the owner
- **Your update reports reach AnIdeaLab now.** Until now a report went only if someone ran the "Send brain update reports" workflow by hand; a push sent nothing, though the run said it passed. Your agent sends any that waited, once, after this update.
- **Matt's testing account** (`diagnoticsanidealab`): your brain's accounts note gets a line for it, and the setup check names it instead of calling it "others", if you've added it to your brain. If you haven't, your agent leaves the line out. It's your choice whether to add it; Matt asks you himself.
- Nothing else changes, and nothing runs on your PC.

## What changed, and why
- **Reports send on a push** (`skills/brain-spec/brain_update.py`, `send`). On a push, `send` worked out which reports the push added from the file lists in GitHub's push event. GitHub leaves those lists out of the event it gives Actions ([its changelog, 16 Oct 2019](https://github.blog/changelog/2019-10-16-changes-in-github-actions-push-event-payload/)), so it always found none, printed "No reports to send." and passed. A brain's update 2 report found it: its push and update 1's had both passed and sent nothing, and its agent sent them by running the workflow by hand. Now `send` fetches the commit from before the push and asks git which reports changed between it and the commit pushed. If git can't say (a new branch, or GitHub doesn't answer), it sends every report, and the inbox replaces any it has already. Matt tried it with a real push on GitHub: the event had no file lists, the old way found nothing, and the new way found both reports the push added. Run by hand, the workflow still sends every report.
- **The brain spec's "Brain updates", step 6:** after pushing, check that the run's log says "Sent" with the report's name, and if it doesn't, run the workflow by hand. Why: the run passed while sending nothing, and nobody saw it for two updates.
- **Matt's testing account** (`knowledge/systems/keys-and-accounts.md`, `skills/my-pc/check-setup.ps1`). Matt decided on 27 Oct 2026 that while the kit is in testing, the installer invites his testing account, `diagnoticsanidealab`, to each new brain as a collaborator, so he can see it and copy it to find what's wrong. Brains made before then don't have it, and Matt is sending their owners one command to add it, for them to run if they agree. The accounts note gets a row for the account, and the setup check says "Matt's testing account can see and change it" instead of counting it among "others who can write". Why: the accounts note says who can reach the brain, and the setup check warns about anyone else who can write, so both should name the account plainly. GitHub gives a collaborator on a personal account's repo read and write, so the row and the check both say so, and how to take it off.

1. **Read both sides of each clash the script printed.** Most brains will have none. If the owner added rows of their own to the accounts note's table, keep theirs and add the testing account's row under the brain's GitHub row. Why: the owner's own lines stay, and the kit's lines go in beside them (the brain spec's "Brain updates").
2. **Check the testing account's row is true.** See whether `diagnoticsanidealab` is a collaborator on this brain's repo or has an invitation to it: your GitHub tool, or `gh api repos/<owner>/<repo>/collaborators --jq '.[].login'` and `gh api repos/<owner>/<repo>/invitations --jq '.[].invitee.login'`. If it's neither, take the row out of the accounts note, and say so in the report. Don't add the account or ask the owner to. If you can't check, keep the row and say so in the report. Why: the note tells the owner and their agents who can reach the brain, so a row for an account that isn't there is wrong, and whether to add it is the owner's choice, made when Matt asks them.

6. **Then run the workflow by hand once** (your GitHub tool's run-workflow method, or "Run workflow" on the repo's Actions tab). It sends every report in the brain, including those from updates 1 to 3, which a push never sent. The inbox replaces any it has already, so sending one twice does no harm. If a run fails, say so to the owner in your reply, with the error, and leave it.
7. **Nothing on the PC.** Nothing here needs to run there.
